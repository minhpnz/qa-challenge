# Findings

Defects and behaviours discovered while building the test suite for
[demoblaze.com](https://www.demoblaze.com/).

Each entry names how it was verified. Thirteen are pinned by an executable test —
a finding with no test attached is a finding that regresses silently. The rest
are covered by documented manual cases in
[`DemoBlaze-Test-Cases.xlsx`](DemoBlaze-Test-Cases.xlsx), because they need
browser chrome, fault injection, or a controlled security environment that a
functional pipeline should not be reaching for.

`test.fail()` is used for confirmed defects: the check keeps running, stays
red-by-expectation, and flips to a loud failure the moment the bug is fixed and
the annotation goes stale. That is deliberately different from `test.skip()`,
which would stop telling us anything at all.

## Test-side lessons captured while stabilising

These were **our** bugs, not the app's, and each is the kind that would have been
"fixed" with a sleep by a less careful hand. They are written up because the fix
is the standard, and the standard is what the team inherits.

| Symptom                                                                        | Real cause                                                                                                                                                                                                                                                                                               | Fix                                                                                                                                                                                                |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Clicking OK on the purchase receipt did nothing                                | SweetAlert only becomes interactive when it adds a `visible` class 500 ms after opening; its own click handler tests for that class and swallows earlier clicks                                                                                                                                          | Wait for the widget's `visible` class — the exact signal its handler reads — not a `waitForTimeout(500)`                                                                                           |
| Cart occasionally showed 2 of 3 added products (Firefox)                       | The loop polled for the alert text "Product added.", which the _previous_ iteration had already produced, so the wait returned instantly and the test navigated away mid-request                                                                                                                         | Reset the dialog watcher per iteration; assert on arrival count, not on a repeated message                                                                                                         |
| Login modal "still open" after a successful login (WebKit)                     | The app hides the modal and immediately calls `location.reload()`; the reload wins the race and the old document still carries Bootstrap's `.show`                                                                                                                                                       | Assert the logged-in state first — it cannot be true before the reload — then assert the modal                                                                                                     |
| Cart total intermittently wrong                                                | The app _appends_ to `#totalp` per line, so a single read can catch a partial sum                                                                                                                                                                                                                        | Web-first `toHaveText`, which retries until the value settles                                                                                                                                      |
| "Empty cart" assertions could never fail                                       | Zero rows is also what an un-fetched page looks like                                                                                                                                                                                                                                                     | Cart navigation waits for the `/viewcart` response before any assertion                                                                                                                            |
| Tests passed alone but failed intermittently at 4 workers                      | `video: 'retain-on-failure'` records **every** test and discards the file on pass — one ffmpeg encoder per worker, each burning 40–60% of a core. The recorder was slowing the tests it was recording until they breached their timeouts                                                                 | Default to `video: 'on-first-retry'`: no steady-state cost, and video is still captured for exactly the runs anyone wants to watch                                                                 |
| A product lookup failed with "not in the catalogue"                            | `GET /entries` returns only page one — 9 of 15 products — so no monitor is ever found through it                                                                                                                                                                                                         | `listAllProducts()` unions the three category endpoints; documented in `api-contract.md`                                                                                                           |
| The order modal's Close button worked locally, flaked on CI                    | Bootstrap sets `_isTransitioning` for the duration of the fade and its `hide()` returns early while that flag is set, so a dismiss click landing mid-transition is silently swallowed. Rare on a fast machine, common on a loaded runner                                                                 | Wait for focus to land on the dialog — Bootstrap moves it at the end of the same transition. Centralised as `BaseComponent.expectModalReady()` after the identical bug turned up in a second modal |
| A `getByRole('button', { name: 'Close' })` lookup was ambiguous in every modal | All three modals carry two controls with that accessible name: the footer button and the header `×`, whose `aria-label` is "Close"                                                                                                                                                                       | Scope by region, provided once as `BaseComponent.footerButton()` / `headerDismissButton()` so a new modal cannot reintroduce it                                                                    |
| Security payload tests passed when written, failed on CI                       | They asserted `"User does not exist."`, but DemoBlaze is a **public sandbox**: `' OR '1'='1`, `<script>alert(1)</script>`, 256 A's, `admin` and `test` are all already registered by other testers, so the API answers `"Wrong password."` The assertion depended on global state the suite does not own | Assert the security property — rejected, no session created, payload never executed — never the incidental wording                                                                                 |
